# Nanobug 插件版本兼容与实验接口设计

日期：2026-11-09。状态：用户已选择 VS Code 的版本兼容与实验接口治理方式，并在 Q18 确认基础接口优先稳定、UI SDK 与自定义绘图接口先实验交付。本文是尚未实现或通过兼容性验收的设计草案；具体函数清单、字段拼写、工具命令与 WASM 接口表示尚未冻结。

用户本轮指令：“使用 vscode 这一套版本控制与实验接口规范，设计我的编辑器插件”。本文件是[总体架构与决策记录](2026-11-08-plugin-architecture.md)的版本管理专项设计。事实依据与 Nanobug 自身的设计补充分开说明。

## 1. 本轮决定及对旧方案的替代

| 事项 | 当前设计 | 与此前讨论的关系 |
| --- | --- | --- |
| 兼容依据 | 插件声明支持的编辑器版本范围；宿主再检查实际所需接口与平台能力 | 不以插件包版本与编辑器版本直接比较大小 |
| 稳定 API | 长期向后兼容，优先新增能力与保留适配；不按固定代数自动删除 | 替代 Q7/Q15 的 N、N−1、N−2 滚动窗口作为淘汰规则 |
| 实验 API | 独立命名、插件显式选择、开发/测试环境显式启用；允许不兼容演进 | Q17 原来的“整个开发期是否豁免兼容”改为逐项区分稳定与实验接口 |
| 当前公开 API 标记 | 继续固定为 `1.0`，只在用户明确手动改版时变化 | 保留用户的开发期版本要求；相同显示标记不是兼容证明 |
| 三个月迁移期 | 稳定接口确实需要不兼容迁移时的提前通知期，且必须有可用迁移路径 | 保留 Nanobug 的期限要求，不是 VS Code 原规，也不代表通知期满自动删除 |
| 初版能力 | 首版 UI SDK、完整覆盖当前 GPUI canvas 公开绘图能力及平台标注继续作为范围要求 | 能力是否可用与是否已承诺稳定是两个维度，不能以“实验”缩减功能范围 |
| Q18 初版稳定范围 | 插件注册/生命周期、文档访问、草稿保存、资源释放等基础接口优先验证并稳定；UI SDK 与自定义绘图接口先作为实验接口提供 | 用户已采纳；实验部分验证成熟后逐项转稳定，不缩减首版功能范围 |

实验接口不承诺固定三个月保持兼容：作者选择实验接口时应知道开发版本升级可能需要同步适配。已经明确标为稳定的接口，即使宿主仍处于开发期，也应遵守稳定契约。当前尚无已发布的 Nanobug 插件接口，不能凭这份设计宣称任何现有接口已经完成稳定化。

VS Code 的参考规则是宿主版本范围、稳定 API 的长期兼容目标，以及单独启用的 Proposed API。其官方资料没有这里的固定 API `1.0` 标记或统一三个月迁移期限。[宿主兼容范围](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#visual-studio-code-compatibility)、[稳定与实验接口](https://code.visualstudio.com/api/advanced-topics/using-proposed-api)

## 2. 对开发者呈现的版本信息

| 信息 | 谁维护 | 用途 |
| --- | --- | --- |
| 插件包 `version` | 插件作者，按 SemVer 发包 | 区分插件更新、选择可用包与更新失败回退 |
| `engines.nanobug` | 插件作者，开发工具校验 | 声明兼容的编辑器产品版本范围，必须提供且不能为 `*` |
| Rust SDK 包版本 | SDK 发布者 | 分发开发期类型、绑定和辅助代码；构建产物记录所用 SDK 与接口需求 |
| 公开 API 标记 `1.0` | 按用户要求手动维护 | 标识当前 API 系列；不替代宿主要求、接口检查或稳定性标记 |
| `enabledApiProposals` | 使用实验能力的插件作者 | 列出选用的实验提案名称；仅声明不等于宿主已提供或批准启用 |

VS Code 对应的前三项分别是扩展包版本、`engines.vscode` 与 `@types/vscode`；Nanobug 使用 Rust/WASM，不引入 Node.js 或 TypeScript 运行环境。Rust SDK 可能包含编译进插件的辅助逻辑，但不能给旧宿主补出它尚未提供的宿主调用。[扩展清单](https://code.visualstudio.com/api/references/extension-manifest)、[VS Code 类型检查实现](https://github.com/microsoft/vscode-vsce/blob/main/src/validation.ts)

版本字段示意如下，仅展示数据关系，不是最终文件格式或完整插件清单：

```toml
id = "example.git"
version = "0.3.0"
enabledApiProposals = ["ui.canvas"]

[engines]
nanobug = "^0.1.0"
```

该例表示插件包自身为 `0.3.0`，支持声明范围内的编辑器，并申请实验提案 `ui.canvas`。`ui.canvas` 是示意名称，尚未决定实际哪些接口归入该提案。范围按明确约定的 SemVer 范围语义解析：`^0.1.0` 不自动包含 `0.2.0`，预发布构建的支持也须明确表达。当前仓库 `Cargo.toml` 的产品版本为 `0.1.0`；本文不修改它，也不把示例当作已发布版本。

SDK 构建工具应结合接口目录、目标基线和真实构建产物，生成模块导入清单、最低所需宿主基线及实验契约记录，并校验清单中的宿主范围。接口目录记录能力首次提供的宿主版本及其语义要求，不能仅从 WASM 函数名推断全部需求。新 SDK 可以面向较旧基线构建，但不能将新宿主必需能力隐藏在较低的版本声明后。允许使用可选新能力的插件，需要真实的降级路径及对应验证，不能仅靠把版本范围写宽。

## 3. 稳定接口的契约

每项稳定接口记录首次提供的编辑器版本、参数与返回值、错误语义、生命周期、事件顺序、线程/异步约束及适用平台。已经承诺的资源释放、草稿确认、文档版本校验、输入与绘图行为也是兼容性的一部分。

后续演进规则：

1. 新能力使用新入口或可协商扩展，旧插件继续获得原先承诺的行为。
2. 弃用首先意味着文档和 SDK 提示推荐替代接口，宿主仍提供旧接口。
3. 不因 GPUI、Wasmtime 或内部结构更新，要求旧插件同步升级。宿主在稳定接口后适配内部变化。
4. 确实无法保留的破坏性变更，需另作明确发布决定；提供迁移说明、可用替代路径和用户要求的三个月提前通知。到期不自动删除，不额外引入此前未采纳的十二个月期限。
5. 保持已有 WASM 产物可用是验收目标的一部分；只证明插件重新编译后通过，不能宣称已经兼容旧插件。

长期兼容不是为每个历史编辑器保留整套运行环境。正常路径为同一宿主实现稳定契约，必要时在相关接口提供适配。仍然遵守每个激活插件一个 runtime 进程；不为接口历史版本另开常驻进程。

这采用了 VS Code 的稳定接口兼容方向；三个月安排、二进制兼容要求与具体适配方式是 Nanobug 的补充设计。[VS Code 稳定承诺](https://code.visualstudio.com/api/advanced-topics/using-proposed-api)、[接口设计原则](https://github.com/microsoft/vscode/wiki/Extension-API-guidelines)

## 4. 实验接口的生命周期

```text
设计提案 → 开发/测试可用 → 修订与验证 → 明确宣布稳定 → 进入稳定 SDK
```

每个实验提案有独立名称、契约说明、适用平台和当前支持的契约标识。插件必须声明选用哪些提案；SDK 的实验绑定也显式开启。宿主在开发版/测试模式下按插件授权启用，并确认自己支持对应契约；未声明或未开放的实验调用不能因绕过 SDK 而成功。

普通稳定插件发布路径只接受稳定接口。实验插件通过开发加载或明确标识的测试包分发，不进入普通稳定发布路径；插件自身标为 preview、发布预览包或使用较新包版本，都不自动获得实验接口权限。当前编辑器非正式版，可提供这条开发/测试路径，不必等正式版才让第三方使用初版 SDK。

Q82 后续已确认 SDK 开发调试默认启动独立测试编辑器实例，使用独立配置和插件数据，允许显式加载本机编译输出并重新加载待测插件。Q83 确认自动编译并重新加载由“设置 → 插件 → xxx 插件”中的逐插件可选开关控制，仅在对应开发调试会话中生效；后续 Q85 确认该开关仅本机保存。初始关闭仍为建议，用户尚未单独指定默认值。该开发入口不改变 Q80 的普通分发范围，也不自动授予实验接口、宿主能力或项目执行权限；仍须核对所选提案与契约。开发实例隔离、设置入口及具体调试协议尚未实现，见[插件架构决策 Q82–Q85](2026-11-08-plugin-architecture.md)。

这参考 VS Code 的 Proposed API 公开开发流程：使用 Insiders、声明 `enabledApiProposals`、获取相应实验类型，在成熟后转入稳定 API。Nanobug 的渠道名称、授权入口与包格式尚待实现；不能宣称 VS Code 的内部白名单与所有特例均已照搬。[Proposed API](https://code.visualstudio.com/api/advanced-topics/using-proposed-api)、[提案稳定化流程](https://github.com/microsoft/vscode/wiki/Extension-API-process)

实验转稳定时，发布稳定入口和首次支持它的宿主版本。插件作者更新 SDK/绑定、调整最低宿主要求、移除相应实验声明并重新发布稳定插件包。已有实验包不会因接口名称相似而自动变成稳定包；迁移工具可以辅助，但不能假定新旧语义相同。

Q18 已确定初版的稳定化优先范围：插件注册/生命周期、文档访问、草稿保存和资源释放等基础接口优先稳定；UI SDK 与自定义绘图接口先以实验方式交付，验证成熟后逐项转稳定。具体函数签名和发布检查仍需设计；采纳这一优先级不代表现有代码已经形成稳定插件 API。未稳定功能的实现、完整度和性能目标仍须满足对应验收要求，“实验”只界定兼容承诺。

## 5. 固定 API 1.0 时怎样防止误加载

两个开发构建都显示 `1.0`，实际实验参数或行为可能不同。设计采用 SDK 自动生成的**实验契约标识**区分，不要求作者手动维护另一套全局 API 版本号：

- 按插件实际使用的提案及其依赖记录契约标识，不把整个宿主构建哈希当作每个插件的唯一兼容条件。
- 宿主列出每个提案可支持的契约标识；不兼容的实验修改更换标识，保留适配时可继续支持旧标识。
- 标识覆盖规范化接口描述和显式的行为契约修订；仅对函数签名求哈希不足以检测行为变化。发布检查要覆盖签名不变但语义变化的情况。
- 编辑器构建 ID 用于定位问题；无关的界面修复或重新构建不应使所有实验插件失效。
- 稳定接口按宿主基线、实际导入及兼容契约校验，不要求插件与最新整套 SDK 契约哈希完全相等。

这不是 VS Code 既有字段，也不是自动把公开 `1.0` 升成 `1.1`；它是 Nanobug 在固定显示版本期间辨认实验构建的配套设计。契约标识不兼容时，提示插件需要适配当前实验接口或选择匹配的开发构建，不能一律报“编辑器版本过低”。

## 6. Rust/WASM 和 IPC 的适配

源码 API、WASM 导入契约、宿主与 runtime 的消息协议、插件业务数据格式是不同对象。SDK 编译成功只证明其中一部分。

| 层次 | 设计约束 |
| --- | --- |
| 源码 SDK | 稳定与实验绑定分开提供；类型与文档来自同一接口定义；明确最低宿主基线 |
| 已构建 WASM | 宿主必须能满足实际导入的名称、类型及契约；不只比对 SDK crate 版本 |
| 跨进程协议 | 在 runtime 接受插件调用前检查消息协议和能力；资源句柄、运行代次与确认语义不能靠 Rust 内存布局隐含约定 |
| 宿主/runtime 配套 | runtime 由编辑器提供；内部 IPC 可随编辑器配套演进，但公共插件契约仍需保留兼容 |
| 业务状态 | 数据格式迁移独立记录；API 检查通过不等于可以安全迁移已有状态 |

若最终选择 WIT/Component Model，给 record/variant 增加成员、修改 import 的类型等是否破坏旧产物，要按实际组件类型兼容规则核实；不能直接照搬 JavaScript“多一个属性就兼容”的直觉。稳定旧导入需继续可满足，新能力必要时使用新的接口类型或入口。可选能力不能以无法解析的强制 WASM 导入出现，否则运行前就会失败，代码中的 `if` 无法补救；应使用可协商调用或独立可选模块。

WIT 不表达全部行为契约；Wasmtime Linker 的 semver 名称匹配也不是最低宿主版本校验，类型匹配仍是实例化条件。具体 WIT/二进制编码选型继续待定。[WIT 说明](https://component-model.bytecodealliance.org/design/wit.html)、[Wasmtime 名称与版本解析](https://docs.wasmtime.dev/api/wasmtime/component/struct.Linker.html#names-and-semver)

## 7. 安装、启用、更新和错误处理

安装/更新先静态检查清单、宿主范围、平台、实际导入及实验契约；不通过则不运行新插件或其状态迁移。已安装插件在宿主升级、包变化或实验授权变化后重新核查；缓存失效不等于先执行未知插件再检查。

| 条件 | 用户可见结果 |
| --- | --- |
| 当前宿主低于插件要求的最低版本 | “编辑器版本过低，请升级”，显示当前和最低要求；保留已有可用插件版本 |
| 自动更新发现最新插件要求更高宿主 | 不用不兼容包替换现有可用包；存在时选取最新兼容版本，并说明新版本的宿主要求 |
| 插件只支持较旧宿主范围 | 说明插件需要更新或不支持当前编辑器，不误报编辑器过旧 |
| 使用实验接口但没有声明或启用授权 | 明确指出实验接口未声明/未启用，提供开发测试路径说明 |
| 实验契约不匹配 | 说明插件与当前开发构建的实验接口不匹配，需要适配或使用匹配构建 |
| 必需平台能力缺失 | 说明具体平台/能力限制；不能通过假实现掩盖 |
| 预先声明的可选能力缺失 | 按已实现的降级路径运行；没有降级路径的强依赖仍阻止启用 |
| 新版本接管前启动或迁移失败 | 按 Q14 恢复上一兼容可用包及对应状态，保留宿主最新草稿 |

兼容检查、实验接口声明和宿主实际权限分别承担不同职责，不能互相替代。本文不新增文件、网络、原生工具等完整权限方案。

## 8. 启动性能与故障隔离

安装和构建阶段准备元数据与契约记录，宿主启动读取小型安装索引与内置支持表。普通启动不得为版本校验先执行全部插件、联网查询版本、遍历所有 WASM 或启动全部 runtime。

缓存按插件内容、宿主支持契约集合、平台和实验启用状态失效；需要重查的模块在实际执行前完成后台/受预算的检查，核心正文先可编辑。这里不增加“先实际使用才激活”的第二道条件：配置选中的兼容模块仍直接进入既定加载调度。仅不兼容模块或其不可缺少的所属插件被阻止，诊断不阻塞正文编辑。

运行时协商在进程启动/能力变化时完成，普通绘图与输入调用使用已解析的调用表，不逐次执行 SemVer 解析。稳定兼容适配不要求常驻多个宿主或多代 SDK 进程。现有项目生命周期、崩溃退避、草稿持久化、更新回退和完整画布范围继续按已确认设计执行。

这些是控制成本的方案，尚无性能测量；保留启动到可编辑 P95 热缓存 ≤300 ms、真正冷启动 ≤1 s 的原定初始验收目标。

## 9. 发布前需要验证的行为

以下为必要验证设计，本轮没有运行测试：

- 保留若干旧稳定插件的原始 WASM 产物，在新宿主上验证调用、输入、事件、资源释放与恢复行为，不只重新编译源码。
- 在插件声明的最低支持宿主和最新宿主验证行为；若仅在最新版本测试，不能证明最低要求准确。
- 旧宿主收到需要新能力的插件包时，阻止启用并显示升级原因；已有可用版本和业务状态保留。
- 实验未声明、未授权、契约不匹配时，在执行相关调用前明确拒绝；两个都显示 `1.0` 的构建不能因此误放行。
- 更新无关宿主代码不导致全部实验插件失效；稳定 API 新增能力不导致旧插件因整表哈希变化被拒绝。
- SDK 构建产物与实际导入不一致、强制导入伪装可选、类型匹配但行为被破坏，都有检查或回归用例。
- 校验与更新失败、首次启用、宿主升级后的缓存失效，不破坏正文可编辑目标与原先回退规则。

## 10. Q18 已确认：初版稳定接口范围

用户已回答“采纳”：优先验证并稳定插件注册/生命周期、文档访问、草稿保存和资源释放等基础接口；UI SDK 与自定义绘图接口在当前开发阶段先作为实验接口交付，验证成熟后逐项转稳定。

首版仍完整覆盖当前 `gpui-pre 0.3.10` canvas 的公开绘图能力，平台专属能力单独标明；既定 SDK 文字/布局自动接入全局光标的目标继续适用。早期使用实验绘图接口的插件可能需要随开发版升级调整代码。具体输入控件、绘图类型和参数并未因此全部冻结为稳定接口；稳定基础接口的实际定义与验收仍须完成。
