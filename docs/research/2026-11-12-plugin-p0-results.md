# Nanobug 插件 P0 验证报告

2026-11-12，工作区分支 `codex/plugin-p0`，基线 `d1cadbf`。本阶段用真实 Nanobug 窗口和测试插件验证启动、输入、进程恢复与项目关闭。构建和复现方式见[实验入口](../../experiments/plugin-probe/README.md)，绘图范围见[固定 GPUI 版本的逐项清单](2026-11-12-plugin-p0-gpui.md)。

## 已验证的行为

| 验收项 | 实际结果 | 本机证据 |
| --- | --- | --- |
| P0-01 分开记录就绪 | 打开含匹配条件的项目，正文可编辑后自动准备规则和插件，无需输入。记录进程创建、平台与字体、首个场景、正文就绪、插件输入区、首幅画面和业务结果 | `measure-pwxrusj5/result.json` 及逐次 JSONL |
| P0-02 进程隔离 | 宿主、规则、WASM 为三个不同进程。强制结束实际 WASM 进程后，正文仍能输入。前台测试保存成功，文件内容与预期一致 | `smoke-nk9qqcy1`，最后版本的窗口消息复测 `smoke-g_1_k228` |
| P0-03 中断和慢读取 | JS 忙循环约 20.03 ms 后退出。WASM 循环运行约 87.89 ms，同一插件的新界面在循环开始后约 43.17 ms 已呈现。控制性慢读约 5.50 s，规则在约 5.00 s 超时，另一项目和正文继续工作。宿主仍追踪约 497 ms 才结束的读取，丢弃晚到数据 | `smoke-g_1_k228`、`slow-read-zg0q3lu3`，另有真实 worker 管道测试 |
| P0-04 文字、光标和输入法 | 宿主排版显示中文和 Emoji，插件离线时输入到下一次布局/场景回调约 12.50 ms。微软拼音前台测试中，切回正文取消预编辑，紧接的 `i` 生效，回到插件后候选字上屏 | `smoke-g_1_k228`、前台拼音 `ime-0tzra5js` |
| P0-05 宿主确认与恢复 | 进程退出前已有 10 字节输入，退出后又确认 3 字节。重启后取回精确的 13 字节草稿，新的 worker 还向宿主注入旧代次画面，宿主明确丢弃后呈现当前版本。一次恢复约 1.07 s，含 1 s 退避 | `smoke-g_1_k228` |
| P0-06 独占资源 | 两个打开项目共享同一进程，各有独立 Store。关闭后从 2 降到 1，另一个项目继续绘制并保持进程。最后从 1 降到 0 并正常退出。管道测试也覆盖关闭时排队的业务工作 | `smoke-g_1_k228`、[真实进程用例](../../experiments/plugin-probe/tests/process.rs) |
| P0-07 绘图边界 | 已对照固定版源码，列出公开入口、对应数据和平台条件。P0 的纯色矩形、文字、宿主布局及输入已有真实窗口证据 | [GPUI 能力清单](2026-11-12-plugin-p0-gpui.md) |
| P0-08 选型依据 | 用 Windows Release 实验验证进程通信、规则中断、宿主确认、恢复和独立 Store 释放。暂用下述引擎与实验协议，后续按证据收敛公共接口 | 本报告下节、[实验协议](../../experiments/plugin-probe/wire/src/lib.rs) |

原始记录在本机 `test-output/plugin-probe/`。前台保存与中文拼音使用真实 Windows 键盘路径。之后桌面锁屏，最后版本用发往测试 HWND 的窗口消息复测输入、恢复和关闭保存。最后版本的真实拼音候选及预编辑中途退出组合需要在前台复测。12.50 ms 到宿主场景回调，屏幕物理呈现延迟另测。

## 启动初测

Windows 11 26200，Ryzen 9 9950X3D，约 62 GiB 内存，RTX 5080、120 Hz，ZHITAI TiPro9000 NVMe，平衡电源模式。使用同一 Release 宿主，零插件与一个匹配插件交替，每组 20 次，各丢弃一次预热。系统缓存为热，桌面处于锁屏状态，测量期间没有本任务的编译。WASM 每次由新进程编译小型 fixture，未配置编译缓存。计时从 Windows 进程创建到宿主记录的就绪点，正文是同一个小型 README。

| 计时点 | P50 | P95 | P99 |
| --- | ---: | ---: | ---: |
| 空插件，正文可编辑 | 221.7 ms | 228.6 ms | 233.2 ms |
| 一个插件，正文可编辑 | 221.8 ms | 240.5 ms | 259.4 ms |
| 一个插件，插件输入区就绪 | 328.7 ms | 347.6 ms | 371.2 ms |
| 一个插件，首个有效画面 | 336.8 ms | 355.8 ms | 379.7 ms |
| 一个插件，首个业务结果 | 324.2 ms | 342.3 ms | 365.1 ms |

先前和 Debug 编译同时运行的前台初测中，正文 P95 分别为 519.7 ms 和 508.7 ms，记录在 `measure-34dngu3c`。这组说明机器负载对该场景影响较大。P7 仍需在前台、真冷/热系统缓存及编译缓存矩阵中，以 50 个安装、典型 10 个活跃插件完成正式验收。20 次样本的 P99 只是当前最大值。

本表产物的 SHA-256 为 `nanobug.exe` `F69133D732AAA9126718BB9DEBC072682D39C650B4E42BC917CBDF5FAAE31FC4`，`nanobug-probe-worker.exe` `529DF796AE30FBE0A5654A7146C8F1CADECCDB69C340A4C4495F386285133048`。

## 本阶段的接口与选型

| 方面 | 本阶段做法 | 下一阶段仍需验证 |
| --- | --- | --- |
| JS 引擎 | QuickJS，通过 `rquickjs 0.14.0`。两个独立求值上下文可并行。JS 显式请求一个 Promise，宿主选择允许的文件，执行片段之间停计约 20 ms 的执行预算 | 验证线程 CPU 时间和中断误差。当前以累计执行片段的经过时间近似计算。真实文件系统阻塞取消仍需按平台处理，模拟慢读没有提前释放占用。一个共享上下文的简单方案会让同步 JS 争用同一执行位置。 [rquickjs 运行时说明](https://docs.rs/rquickjs/0.14.0/rquickjs/) |
| WASM 引擎 | Wasmtime 50.0.0 与 Cranelift。每个活跃测试插件一个进程，模块编译一次，每项目单独 Store，业务任务单独 Store 和有界队列 | 测生产包、受控编译缓存及各平台运行成本。Wasmi 解释器同样提供 fuel，可作为体积和首次加载的对照，尚未实测。P0 worker 二进制约 13.3 MiB。 [Wasmtime 运行时](https://docs.wasmtime.dev/api/wasmtime/) · [Wasmi fuel](https://docs.rs/wasmi/latest/src/wasmi/engine/config.rs.html) |
| WASM 接口 | 固定内置 `.wat` 编译为 WASM。`draw` 接收 UTF-8 字节长度，宿主向受限内存区写入输入并读取完整文本请求。后台 `work` 走独立调用 | 对照 WIT/Component Model 和自定义 core WASM ABI 的产物兼容、版本协商与复制开销，确定正式清单、能力及文档位置契约。此处的内存偏移和导出符号仅用于实验 |
| 进程消息 | 子进程管道上的 UTF-8 JSON 行，单条最多 16 KiB。规则用评估 ID，界面用作用域、运行代次和输入修订。完整状态可合并，宿主核对当前输入后才接收画面 | 对照长度前缀二进制或共享内存的实测开销，按真实载荷选用。正式协议需要握手、错误码、资源授权和队列繁忙处理。P0 的 1024 字节草稿和 256 字节文件结果只用于样例 |
| 验证入口 | 通过真实 worker 管道和 `nanobug.exe --plugin-probe` 验证公开行为，不逐层模拟内部对象 | 继续从安装、规则、文档与 UI 的真实行为验证。故障夹具及启动时间戳可复用 |

首版稳定/实验 API 及公开 `1.0` 规则按[实现规格](../插件系统初版实现规格.md)。P0 建立了技术证据，P1 使用正式 ZIP 清单、身份和兼容性检查打开安装路径，P3 做完整绘图能力逐项对照。

## 检查

工作区测试共 131 项通过，其中 4 项启动真实 worker 进程。Clippy、格式检查、无实验功能编译检查和 Release 双程序构建通过。两路审查依据工作树差异核对规格和代码，修正了规则占用槽过早释放、关闭后排队任务、输入超限反馈、提示重叠和标签键路由。变更留在本地工作树。
