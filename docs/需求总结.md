# Nanobug-V2 功能需求与方案方向

整理日期：2026-11-06。来源：GPUI 纯文字 UI 方案讨论。

Nanobug-V2 的目标是一个用 Rust 开发、运行于独立桌面窗口的字符网格编辑器：具有 LazyVim 一类界面的布局与键盘操作体验，追求启动即编辑、流畅的跨区域光标，以及插件自主绘制界面的能力。插件按功能模块加载，用户通过轻量 JS 规则选择何时启用各模块。

本文区分三种状态：**明确需求**来自用户表达；**方案方向**是本次讨论形成的实现建议；**待定**表示需要后续设计或测量。独立 Demo 的完成不代表 V2 已实现。旧版 Nanobug Editor 的实现不作为 V2 的架构约束。

## 明确的产品目标

| 编号 | 需求 | 预期效果 |
| --- | --- | --- |
| R01 | 原生字符网格界面 | 用文字、颜色及字符边框组织编辑区、文件树、状态栏、搜索与弹层，外观接近 LazyVim |
| R02 | 极快启动与低延迟编辑 | 追求“秒开”，首屏和编辑输入不等待插件重型模块、语言服务或索引初始化 |
| R03 | 全窗口平滑光标 | 光标在编辑区、文件树和弹层之间连续移动，视觉体验参考 Neovide |
| R04 | 内部窗口布局调整 | 支持分栏、改变尺寸、切换焦点、交换或移动内部窗口位置 |
| R05 | 窗口与弹层透明模糊 | 能透出模糊的桌面和后方窗口，正文与字符边框保持清晰 |
| R06 | 插件完全自主实现界面逻辑 | 插件自行实现文件树、搜索框、列表等内容和行为，不强制采用宿主控件库 |
| R07 | Rust 插件与通用安装包 | 插件由 Rust 编写，希望同一插件包可供 Windows、macOS、Linux 使用 |
| R08 | 分模块按需加载 | UI、业务、解析和高亮职责分开，不能等整个大型插件初始化后才显示界面 |
| R09 | 每插件一个 runtime | 宿主本体与各已激活插件 runtime 分进程；同一插件的模块不各自创建一个进程 |
| R10 | 用户可编辑的启用规则 | 插件提供默认规则，用户能在设置管理中编写条件并覆盖默认行为 |
| R11 | 每插件独立 JS 配置 | JS 仅负责判断对应模块是否启用，普通用户电脑不需要 Rust 编译器 |
| R12 | 按语言和项目条件启用 | 根据文件类型、项目文件、依赖版本选择插件模块；嵌入代码块可调用对应语言高亮能力 |

多个侧边或底部窗口的管理，以及快捷移动窗口，是后续布局设计的重要问题。用户特别提出“只想看到一个底部窗口时，打开另一个不应被迫同时占据两块区域”；默认是否采用互斥显示仍未定案。

“纯字符界面”指主要产品外观，不代表必须运行在终端、逐字符创建控件，或禁止插件绘制图片和其他图形。完整 Vim 命令兼容、以 Neovim 作为编辑核心、终端后端或 Web 版本，均未确认为本轮目标。

## 字符网格与渲染

### GPUI 路线

当前方案方向为 **GPUI 加自定义字符网格层**。egui 曾作为对比对象，尚无同条件实测证明 GPUI 的整体编辑器性能必然更高。GPUI 版本、是否采用 GPUI Kit 中的部分能力，需要 V2 自行确定。

按编辑窗口、插件面板和浮窗等稳定区域划分独立缓存视图；每个视图内保留网格状态与文字行排版缓存。全局布局、坐标、层级和焦点统一管理。

```text
原生窗口
├─ 布局与输入管理
├─ 编辑窗口 A：缓存视图 → canvas → 网格与文字行缓存
├─ 编辑窗口 B：缓存视图 → canvas → 网格与文字行缓存
├─ 插件面板：缓存视图 → canvas → 插件提交的绘制数据
├─ 搜索等弹层：独立缓存视图
└─ 全窗口光标层：独立动画与绘制
```

这里的“网格”是保存字符、样式和位置的逻辑数据，“canvas”是绘制入口。两者不必一一对应；不要为每个字符或每一小块内容建立一个 GPUI Entity。

### 更新与缓存边界

需要区分状态更新、排版重算、场景构建和 GPU 呈现。单个网格可以独立更新数据、只重算变化行；GPUI 视图缓存可以复用未变化区域的场景记录。这不等于 GPU 只改动该区域像素。

本次使用的 GPUI 快照中，标准 `canvas` 没有“保留其他像素，只修改指定脏矩形”的内置接口。多视图缓存也不是自动生成一张张持久离屏纹理。整帧仍需合成与提交。

方案方向：

- 按行或连续样式片段批量绘制，避免逐字符跨语言、跨进程调用。
- 缓存可见行排版，并明确文本、样式、字体、宽度、缩放等失效条件。
- 内容、选区、光标等按实际更新频率划分缓存边界。
- 隐藏或未变化的面板尽量不重算；窗口缩放和布局调整只使受影响内容失效。
- 离屏纹理缓存或后端局部重绘作为测量后再决定的优化，不作为已有能力。

### 光标和文字输入

采用一个覆盖全窗口的光标层，内部窗口只声明逻辑光标位置。宿主把区域坐标、滚动偏移和字符单元换算成窗口坐标，驱动光标插值。

逻辑焦点及输入位置应立即切换，视觉动画独立进行；连续跳转从当前显示位置继续运动。IME 候选位置跟随逻辑输入位置，不能等待动画结束。动画完成后停止主动请求帧。

生产实现需要处理中文双宽字符、组合字素、Emoji、字体回退、滚动、选区、UTF-8/UTF-16 转换和 IME 预编辑。独立 Demo 的中文文本验收不等于各种输入法与复杂 Unicode 场景均已通过。

## 透明与模糊

明确需求是整个编辑器和弹层能够透出模糊桌面。已有 Windows Demo 使用系统 Acrylic 背景，文字透明度与背景透明度分别处理。

弹层效果必须区分两种语义：

| 效果 | 本次状态 | 实现方向 |
| --- | --- | --- |
| 弹层直接透出同一份模糊桌面 | 已在独立 Demo 中演示 | 共享原生窗口背景，并裁剪弹层下方正文 |
| 弹层模糊下面的代码和文件树 | 尚未确认为必须实现 | 需要应用内部背景采样、离屏绘制与模糊合成 |

透明模糊不要求只使用一个 canvas。多 canvas 仍可位于同一原生窗口内。Windows、macOS、Linux 的材质与降级表现需分别设计和验收，不能把 Windows 演示当作跨平台保证。

## 插件自定义绘制接口

### 插件拥有的职责

插件应能独立实现界面状态、内部布局、命中测试、键盘和鼠标交互、选区、滚动，以及绘图指令生成。插件可以使用自己的 UI 抽象，或直接使用底层绘图能力。

宿主不通过一份固定的“文件树、搜索框、列表”组件清单来限定插件界面。高层字符控件可以由 SDK 或插件库提供，但使用它们应是可选的。

### 宿主提供的通用机制

候选接口可概括为“绘制区域 + 输入事件 + 绘制批次 + 资源句柄”：

| 能力 | 需要表达的内容 |
| --- | --- |
| 区域生命周期 | 创建、尺寸变化、显示隐藏、销毁、资源归属 |
| 绘图 | 文字、填充、描边、路径、图像及所需裁剪和变换能力 |
| 字符网格快捷接口 | 写入字符与样式、更新行段、滚动区域、声明光标 |
| 输入 | 键盘、文本输入、鼠标、滚轮、焦点、IME 接入 |
| 资源 | 字体测量、图片或其他绘制资源的创建、引用和释放 |
| 帧提交 | 批量提交 DrawList 或网格增量，复用未变化内容 |

这些是待定义的协议能力，不是已有 SDK API。跨进程或 WASM 插件不会直接拿到 GPUI 的 `Window`、`App` 引用或 Rust 绘制闭包。插件提交数据，宿主执行真实 GPUI/GPU 绘制。

用户要求的自由度是“插件能自己实现 canvas 能表达的界面逻辑”。协议仍需逐项定义允许的绘图能力；着色器、任意 GPU 回调、外部纹理或应用内部模糊等，不能仅凭一个 `DrawList` 名称就声称已全部支持。

## 插件进程与模块结构

### 进程结构

用户希望看到如下关系：

```text
Nanobug 编辑器
├─ 宿主本体
├─ xxx 插件 runtime
└─ xxx 插件 runtime
```

方案方向为：编辑器分发一个通用原生 runtime 程序，为每个已激活插件启动一个实例；插件内部多个模块按需加载，不为 UI 和业务分别打包一个 EXE。runtime 不重复创建 GPUI 渲染器，最终显示由宿主负责。

UI 事件处理不能被同一 runtime 内的索引等重任务阻塞。runtime 按需启动并复用，插件退出或被禁用时回收其资源。原生 LSP、工具等受管依赖可能额外产生进程；Windows 任务管理器的精确分组和显示名称需要实机验收，父子关系本身不能保证展示形式。

### 跨平台包与独立 WASM

后续讨论采用的方案方向是 **一个安装包，多个独立 WASM 模块**，替代先前提出的 Windows DLL 方案。

```text
demo-plugin.zip
├─ plugin.toml
├─ modules/
│  ├─ ui.wasm
│  ├─ language_server.wasm
│  └─ formatter.wasm
├─ grammars/
│  └─ language.wasm
├─ queries/
│  ├─ highlights.scm
│  └─ injections.scm
├─ rules/
│  └─ defaults.js
└─ assets/
```

上面的目录和文件名是结构示意，包版本、协议、WIT、构建 target 和正式清单字段尚未冻结。简单插件可以只有一个模块；纯资源包无需附带空 WASM。

Rust 源码可以使用 workspace，将 UI、业务和轻量共享契约分开。UI 模块不得经共享依赖重新链接重型业务代码，其初始化也不得等待业务模块。插件作者使用 Rust 编译工具链，最终用户只安装已构建的包。

安装单位是插件包，进程隔离单位是插件 runtime，按需加载单位是模块或资源。平台无关 WASM 通过一致的宿主接口运行；原生 LSP 和工具仍需按平台准备。

### 哪些内容需要可执行 WASM

| 内容 | 方案方向 |
| --- | --- |
| Rust 插件 UI 状态与交互 | 可独立编译为 UI WASM，打开视图时加载 |
| Rust 业务功能 | 按有独立生命周期的职责拆为 WASM |
| Tree-sitter grammar | 独立 grammar WASM，使用 Tree-sitter 对应 ABI 和加载器 |
| 高亮查询、注入查询、主题、图标、图片、代码片段 | 普通资源，不必为每项编译一个 WASM |
| JS 启用条件 | 由嵌入式 JS 引擎执行，无需编译成 WASM |
| 语法树、高亮范围、DrawList | 运行时数据，不是独立插件可执行文件 |
| GPUI 绘制、字体排版、原生输入、全局光标 | 宿主原生实现 |
| LSP 或其他原生工具 | 受管外部程序或依赖，不强制转换为 WASM |

Tree-sitter grammar 与普通业务 WASM Component 不是同一种接口。解析服务究竟在对应插件 runtime 内还是独立宿主服务执行、怎样共享文档版本，需要专门设计，不能仅按文件扩展名决定加载方式。

### 可条件启用的模块

模块 ID 由插件声明，优先按职责命名，例如 `ui`、`language_server`、`grammar`、`preview`、`formatter`、`linter`、`indexer`、`search_provider`、`commands`、`project_discovery`、`file_provider`、`source_control`。

业务明确时也可叫 `export_pdf`、`link_checker`、`history`、`blame`。早期示例中的 `logic` 只是泛称，不是必须保留的模块类型。

补全、悬浮、跳转、重命名和诊断可能共用一个语言服务，不必机械地拆成多个 WASM。拆分依据是加载时机、依赖和执行生命周期。

## JS 模块启用规则

### 配置体验

用户在设置管理中选择插件并编辑其 JS 规则；每个插件有独立配置，插件提供默认规则。用户已表示模块 ID 的补全提示由插件提供，本轮不继续展开该话题。

概念目录为 `用户配置根/plugins/<插件ID>.js`。实际配置根位置待定，不从这条相对路径推导旧项目的数据目录规则。

JS 只做条件判断与模块选择，Rust 宿主负责权限检查、生命周期和实际加载。复用 JS 引擎及已加载函数；按文件、项目依赖、设置变化等事件重新评估，不让 JS 参与每帧字符绘制或光标动画。

### 拟定接口示例

以下配置语法是讨论方案，不是已实现接口。

```js
// javascript.js：正文或嵌入代码块需要 JavaScript 时启用对应 grammar。
export default {
  modules: {
    grammar: ctx => ctx.languages.includes("javascript"),
    language_server: ctx => ctx.file.extension === ".js",
  },
};
```

```js
// vue3.js：示例采用已解析的 Vue 主版本，未知版本不匹配。
function matchesVue3Project(ctx) {
  return (
    ctx.project.rootFiles.includes("package.json") &&
    ctx.project.dependencies.vue?.major === 3
  );
}

export default {
  modules: {
    grammar: ctx => ctx.languages.includes("vue") && matchesVue3Project(ctx),
    language_server: ctx => ctx.file.extension === ".vue" && matchesVue3Project(ctx),
  },
};
```

候选上下文包含文件扩展名、当前及嵌入语言、项目根文件列表、解析后的依赖版本。宿主缓存这些信息，批量传给脚本；不要求脚本每次自行读文件和解析依赖。

规则语义方向：`true` 允许当前上下文按需启用，`false` 不为当前上下文启用，缺省或 `undefined` 继承插件默认规则。宿主汇总所有文档的需求；一个文档返回 `false`，不能停掉另一个文档仍在使用的模块。

用户只覆盖部分模块时，其余保留默认配置；修改成功后重新评估，出错则显示错误并保留上一份有效配置，插件更新保留用户配置。具体优先级、资源释放策略、脚本执行预算和诊断格式待定。

### 语言选择和嵌入高亮

用户举出的场景必须覆盖：

1. `.js` 调用 JavaScript 对应模块，`.md` 调用 Markdown 对应模块。
2. 项目根包含 `package.json`，依据 Vue 版本选择 Vue 插件。
3. Markdown 代码块识别出其他语言后，只加载必要的语言解析与高亮资源。

Vue 条件存在需要确认的语义差异：用户原话是“版本大于 3 用 Vue3，否则 Vue2”，后续示例采用“主版本等于 3 / 等于 2，未知不匹配”。正式规则必须明确是 `>=3`、`>3` 还是 `major === 3`，以及未知版本、版本范围和多个依赖位置如何处理；不能把未知版本自动归为 Vue2。

Markdown 的方案流程为：Markdown grammar 识别代码块 → 得到语言标识 → 更新语言上下文 → 评估对应插件规则 → 加载该语言 grammar 与查询 → 对块内容高亮。此过程不应默认启动该语言插件全部业务模块或 LSP。

基础语法高亮与 LSP 语义高亮可以叠加；grammar、查询、语法树、高亮范围和最终 GPU 绘制需要分清职责。语言注入不等于完整的嵌入语言补全、跳转和格式化，后者另需设计。

## 内部窗口与插件布局

### LazyVim 参考结论

本次调查区分了 Neovim 核心窗口、插件内部布局和 Edgy 等可选布局管理器：普通分栏可嵌套组合，浮窗覆盖在分栏之上；插件可以计算一组内部窗口的几何位置。可选 Edgy 可把面板按上下左右分组，但不会自动给所有插件提供“底部永远只显示一个”的通用互斥策略。

V2 可借鉴窗口与内容分离、嵌套分栏、浮层坐标和统一焦点管理，而不照搬所有 LazyVim 插件布局。已制作的 34 种布局图例是参考图鉴，不是 34 项全部必须实现的功能清单。

### 宿主和插件的布局边界

方案方向：宿主管理顶层分栏树、区域分配、焦点、尺寸、层级和窗口移动；插件管理分配区域内部的布局与交互。插件通过通用接口申请侧边区域、底部区域或浮层，不能绕过宿主各自抢占全局空间。

需要设计的操作包括：方向切换焦点、调整尺寸、交换窗口、移动到某方向、显示隐藏、关闭和恢复。Neovim 的 `Ctrl+w` 加大写 `H/J/K/L` 可作为“移动窗口”参考，`Ctrl+h/j/k/l` 可作为“切换焦点”参考；V2 的实际键位没有定案。

### 多面板策略

候选策略如下：

| 策略 | 表现 | 状态 |
| --- | --- | --- |
| 单活动面板 | 打开新面板时隐藏原面板，切回后恢复原状态 | 最直接回应用户的底部重复占位顾虑 |
| 标签或选择器 | 多面板注册到同一区域，用户切换当前项 | 与单活动模式可组合 |
| 多面板并排或堆叠 | 同一区域同时显示多个内容 | 适合用户明确要求同时查看 |

默认策略、用户如何切换策略、面板最小尺寸、空间不足、布局持久化、插件自己的多窗口组如何移动，均为待定项。隐藏面板也不等于关闭文档、销毁插件或终止后台任务，生命周期需单独规定。

原型固定使用 `gpui-pre` / `gpui-pre-platform 0.3.10`，不是 V2 已确定的依赖版本。Glass Editor 不保存真实文件，没有插件加载器、正式插件 SDK 或语言服务。其 IME 适配已接入，但没有完整覆盖所有输入法组合场景。

性能报告于 2026-11-05 在本机测量，累计 13,824 个有效帧，36 组像素比对一致。64 网格时，“状态更新到 GPUI 场景构建完成”的 CPU 中位数如下：

| 每帧变化 | 单画布与网格缓存 | 多画布与视图缓存 |
| --- | ---: | ---: |
| 光标与当前行 | 0.669 ms | 0.401 ms |
| 一个网格修改一行 | 0.696 ms | 0.411 ms |
| 四分之一网格各修改一行 | 0.825 ms | 0.651 ms |
| 全部网格各修改一行 | 1.299 ms | 1.512 ms |
| 全部网格换位置 | 0.691 ms | 0.824 ms |
| 全部正文持续变化 | 2.828 ms | 2.995 ms |

这支持“局部变化时独立视图缓存有收益，全体变化时多视图开销可能更大”的局部结论。数据不含透明模糊、重叠弹层、插件 IPC、WASM 冷启动、GPU 硬件时间或输入到实际显示延迟；不能换算为完整编辑器 FPS，也不能证明秒开。

## 后续需要确定和验证的事项

| 事项 | 需要形成的结果 |
| --- | --- |
| 性能目标 | 定义冷启动、热启动、首帧、首个可编辑状态、输入延迟、滚动和内存的测量口径及阈值 |
| GPUI 接入 | 确定版本、canvas 与自定义 Element 的边界，以及稳定的视图缓存粒度 |
| 插件绘图协议 | 明确原语、资源、输入、坐标、层级、更新批次和失效规则 |
| 模块加载 | 确定 WASM ABI、模块依赖、异步调用、失败隔离、取消、卸载及缓存机制 |
| JS 规则 | 确定上下文、覆盖优先级、执行预算、诊断，以及多个提供者冲突的处理 |
| 语言服务 | 确定 Tree-sitter 执行位置、文档版本同步、嵌入语言发现和高亮结果应用 |
| 布局 | 确定底部互斥默认值、多个侧边面板、插件多窗口组、尺寸和移动策略 |
| 平台效果 | 验收各平台透明模糊与降级，以及 Windows 任务管理器展示 |
| 编辑器基础 | 真实文件读写、大文件、完整 IME、辅助功能等需单独形成生产规格 |

建议先沿用独立原型验证 UI 底座和测量口径，再用一个小型自绘插件贯通 runtime、UI WASM、业务 WASM 和批量绘图，随后加入 JS 规则及嵌入语言高亮。这是后续工作的建议顺序，本次授权范围是整理文档和转入新会话。
