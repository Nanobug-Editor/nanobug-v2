# Nanobug-V2 功能需求与方案方向

整理日期：2026-11-06。插件方案最近更新：2026-11-11。来源：GPUI 纯文字 UI 方案讨论及后续插件架构访谈。

Nanobug-V2 的目标是一个用 Rust 开发、运行于独立桌面窗口的字符网格编辑器：具有 LazyVim 一类界面的布局与键盘操作体验，追求启动即编辑、流畅的跨区域光标，以及插件自主绘制界面的能力。插件按功能模块加载，用户通过轻量 JS 规则选择何时启用各模块。

本文区分三种状态：**明确需求**来自用户表达；**方案方向**是本次讨论形成的实现建议；**待定**表示需要后续设计或测量。独立 Demo 的完成不代表 V2 已实现。旧版 Nanobug Editor 的实现不作为 V2 的架构约束。

## 明确的产品目标

| 编号 | 需求 | 预期效果 |
| --- | --- | --- |
| R01 | 原生字符网格界面 | 用文字、颜色及字符边框组织编辑区、文件树、状态栏、搜索与弹层，外观接近 LazyVim |
| R02 | 极快启动与低延迟编辑 | 追求“秒开”，首屏和编辑输入不等待插件重型模块、语言服务或索引初始化 |
| R03 | 全窗口平滑光标 | 光标在编辑区、文件树和弹层之间连续移动，视觉体验参考 Neovide |
| R04 | 内部窗口布局调整 | 支持分栏、改变尺寸、切换焦点、交换或移动内部窗口位置 |
| R05 | 窗口与弹层透明模糊 | 能透出模糊的桌面和后方窗口，正文与字符边框保持清晰 |
| R06 | 插件完全自主实现界面逻辑 | 插件自行实现文件树、搜索框、列表等内容和行为，不强制采用宿主控件库 |
| R07 | Rust 插件与通用安装包 | 插件由 Rust 编写，希望同一插件包可供 Windows、macOS、Linux 使用 |
| R08 | 分模块按需加载 | UI、业务、解析和高亮职责分开，不能等整个大型插件初始化后才显示界面 |
| R09 | 每插件一个 runtime | 宿主本体与各已激活插件 runtime 分进程；同一插件的模块不各自创建一个进程 |
| R10 | 用户可编辑的启用规则 | 插件提供默认规则，用户能在设置管理中编写条件并覆盖默认行为 |
| R11 | 每插件独立 JS 配置 | JS 仅负责判断对应模块是否启用，普通用户电脑不需要 Rust 编译器 |
| R12 | 按语言和项目条件启用 | 根据文件类型、项目文件、依赖版本选择插件模块；嵌入代码块可调用对应语言高亮能力 |
| R13 | 初版跨文件文本修改接口 | 插件提交修改清单，宿主统一检查、预览和应用，支持整组撤销，用于项目级重命名与批量修复 |

多个侧边或底部窗口的管理，以及快捷移动窗口，是后续布局设计的重要问题。用户于 2026-11-11 明确要求目前不讨论布局，底部先默认只占一个窗口，以新面板覆盖切换；标签、分栏及其他布局策略暂缓。

“纯字符界面”指主要产品外观，不代表必须运行在终端、逐字符创建控件，或禁止插件绘制图片和其他图形。完整 Vim 命令兼容、以 Neovim 作为编辑核心、终端后端或 Web 版本，均未确认为本轮目标。

## 字符网格与渲染

### GPUI 路线

当前方案方向为 **GPUI 加自定义字符网格层**。egui 曾作为对比对象，尚无同条件实测证明 GPUI 的整体编辑器性能必然更高。GPUI 版本、是否采用 GPUI Kit 中的部分能力，需要 V2 自行确定。

按编辑窗口、插件面板和浮窗等稳定区域划分独立缓存视图；每个视图内保留网格状态与文字行排版缓存。全局布局、坐标、层级和焦点统一管理。

```text
原生窗口
├─ 布局与输入管理
├─ 编辑窗口 A：缓存视图 → canvas → 网格与文字行缓存
├─ 编辑窗口 B：缓存视图 → canvas → 网格与文字行缓存
├─ 插件面板：缓存视图 → canvas → 插件提交的绘制数据
├─ 搜索等弹层：独立缓存视图
└─ 全窗口光标层：独立动画与绘制
```

这里的“网格”是保存字符、样式和位置的逻辑数据，“canvas”是绘制入口。两者不必一一对应；不要为每个字符或每一小块内容建立一个 GPUI Entity。

### 更新与缓存边界

需要区分状态更新、排版重算、场景构建和 GPU 呈现。单个网格可以独立更新数据、只重算变化行；GPUI 视图缓存可以复用未变化区域的场景记录。这不等于 GPU 只改动该区域像素。

本次使用的 GPUI 快照中，标准 `canvas` 没有“保留其他像素，只修改指定脏矩形”的内置接口。多视图缓存也不是自动生成一张张持久离屏纹理。整帧仍需合成与提交。

方案方向：

- 按行或连续样式片段批量绘制，避免逐字符跨语言、跨进程调用。
- 缓存可见行排版，并明确文本、样式、字体、宽度、缩放等失效条件。
- 内容、选区、光标等按实际更新频率划分缓存边界。
- 隐藏或未变化的面板尽量不重算；窗口缩放和布局调整只使受影响内容失效。
- 离屏纹理缓存或后端局部重绘作为测量后再决定的优化，不作为已有能力。

### 光标和文字输入

采用一个覆盖全窗口的光标层，内部窗口只声明逻辑光标位置。宿主把区域坐标、滚动偏移和字符单元换算成窗口坐标，驱动光标插值。

逻辑焦点及输入位置应立即切换，视觉动画独立进行；连续跳转从当前显示位置继续运动。IME 候选位置跟随逻辑输入位置，不能等待动画结束。动画完成后停止主动请求帧。

生产实现需要处理中文双宽字符、组合字素、Emoji、字体回退、滚动、选区、UTF-8/UTF-16 转换和 IME 预编辑。独立 Demo 的中文文本验收不等于各种输入法与复杂 Unicode 场景均已通过。

## 透明与模糊

明确需求是整个编辑器和弹层能够透出模糊桌面。已有 Windows Demo 使用系统 Acrylic 背景，文字透明度与背景透明度分别处理。

弹层效果必须区分两种语义：

| 效果 | 本次状态 | 实现方向 |
| --- | --- | --- |
| 弹层直接透出同一份模糊桌面 | 已在独立 Demo 中演示 | 共享原生窗口背景，并裁剪弹层下方正文 |
| 弹层模糊下面的代码和文件树 | 尚未确认为必须实现 | 需要应用内部背景采样、离屏绘制与模糊合成 |

透明模糊不要求只使用一个 canvas。多 canvas 仍可位于同一原生窗口内。Windows、macOS、Linux 的材质与降级表现需分别设计和验收，不能把 Windows 演示当作跨平台保证。

## 插件自定义绘制接口

### 插件拥有的职责

插件应能独立实现界面状态、内部布局、命中测试、键盘和鼠标交互、选区、滚动，以及绘图指令生成。插件可以使用自己的 UI 抽象，或直接使用底层绘图能力。

宿主不通过一份固定的“文件树、搜索框、列表”组件清单来限定插件界面。高层字符控件可以由 SDK 或插件库提供，但使用它们应是可选的。

### 宿主提供的通用机制

候选接口可概括为“绘制区域 + 输入事件 + 绘制批次 + 资源句柄”：

| 能力 | 需要表达的内容 |
| --- | --- |
| 区域生命周期 | 创建、尺寸变化、显示隐藏、销毁、资源归属 |
| 绘图 | 文字、填充、描边、路径、图像及所需裁剪和变换能力 |
| 字符网格快捷接口 | 写入字符与样式、更新行段、滚动区域、声明光标 |
| 输入 | 键盘、文本输入、鼠标、滚轮、焦点、IME 接入 |
| 资源 | 字体测量、图片或其他绘制资源的创建、引用和释放 |
| 帧提交 | 批量提交 DrawList 或网格增量，复用未变化内容 |

这些是待定义的协议能力，不是已有 SDK API。跨进程或 WASM 插件不会直接拿到 GPUI 的 `Window`、`App` 引用或 Rust 绘制闭包。插件提交数据，宿主执行真实 GPUI/GPU 绘制。

用户要求的自由度是“插件能自己实现 canvas 能表达的界面逻辑”。协议仍需逐项定义允许的绘图能力；着色器、任意 GPU 回调、外部纹理或应用内部模糊等，不能仅凭一个 `DrawList` 名称就声称已全部支持。

## 插件进程与模块结构

### 进程结构

用户希望看到如下关系：

```text
Nanobug 编辑器
├─ 宿主本体
├─ xxx 插件 runtime
└─ xxx 插件 runtime
```

方案方向为：编辑器分发一个通用原生 runtime 程序，为每个已激活插件启动一个实例；插件内部多个模块按需加载，不为 UI 和业务分别打包一个 EXE。runtime 不重复创建 GPUI 渲染器，最终显示由宿主负责。

UI 事件处理不能被同一 runtime 内的索引等重任务阻塞。runtime 按需启动并复用，插件退出或被禁用时回收其资源。原生 LSP、工具等受管依赖可能额外产生进程；Windows 任务管理器的精确分组和显示名称需要实机验收，父子关系本身不能保证展示形式。

Q71 已确认由宿主统一安排插件加载、编译缓存重建、索引等重任务，以及公共服务和受管工具的相关负载。交互和当前操作优先，后台限量并行，其他项目持续取得执行机会；用户接受繁忙时后台准备可能更慢。配置满足的模块仍自动进入准备，不增加首次使用门槛或闲置回收。并发值与平台限额根据机器配置和实测确定，当前尚未实现或验证。见[插件架构决策 Q71](research/2026-11-08-plugin-architecture.md)。

Q72 已确认可调整的内存保护：先回收可重建缓存、减少新后台任务并限制新增占用，仍无法控制时停止最小范围的超限任务、工具或插件，保留正文与已确认草稿。因内存保护被停止的对象暂停自动重启，提示用户处理或手动恢复；普通崩溃仍按原有限重启规则。默认额度依实测制定，允许用户调整，不因闲置卸载正常插件。紧急中断的外部操作保留结果核对记录，不宣称回滚或自动重做；内存统计包含相关进程与宿主代管资源，实际保护尚未实现和验收。见[插件架构决策 Q72](research/2026-11-08-plugin-architecture.md)。

Q73 已确认在插件详情 Overview 中显示轻量运行概况，复用 Modules 和 Logs：展示最近采样的 CPU、内存、当前及排队任务、准备耗时和恢复或暂停原因，并连接已有的重试、额度调整和日志入口。基础保护监测持续运行，详细采样按需开启并限制频率与保存容量；关闭相应诊断后停止额外采集。查看详情读取已有状态，不额外启用插件或阻塞核心启动与输入。共享资源单独记账，显示采样时间和适用项目，无法准确测量时明确标注；实际开销纳入性能验收。此为已确认设计，尚未实现监测界面或修改独立预览。见[插件架构决策 Q73](research/2026-11-08-plugin-architecture.md)。

Q81 已确认宿主连续启动崩溃后，用户下次打开时进入临时仅核心恢复模式，先能打开文件、编辑和保存，暂停插件及其执行链。保留安装包、有效规则、未应用修改和已保存草稿，提供日志与主动恢复入口；不自动卸载、改写启用规则或重放外部操作。正常启动仍按条件自动安排插件，单个插件或工具故障继续沿用原恢复策略。触发阈值及具体协议独立设计，不套用插件重启次数，也不把启动崩溃直接归因于插件。见[插件架构决策 Q81](research/2026-11-08-plugin-architecture.md)，尚未实现或验收。

Q77 已确认安装时集中说明并确认插件及依赖需要的访问权限，点击 Install 授予页面展示的范围，日常已授权操作不重复询问。主动更新需要新增权限时展示变化并再次确认，未同意则保留已有可用版本；没有新增权限时沿用原更新流程。宿主按调用者、项目和授权范围检查 API，JS 条件脚本继续只做判断；权限记录本地读取，不阻塞启动或增加首次使用门槛。原生外部程序的权限性质单独说明，初版模式已由 Q78 确认，不能由 WASM 限制直接推导。见[插件架构决策 Q77](research/2026-11-08-plugin-architecture.md)，尚未实现权限机制或修改预览。

Q79 已确认首次打开新项目时单独确认是否允许工具执行该项目的构建脚本、过程宏或任务，同一项目记住选择，重开及日常使用不重复询问。核心编辑保存先可用，提示不阻塞输入；未获许可时暂停依赖执行项目代码的功能，部分分析和补全可能受限。`.nb/` 自动读取与受控只读判断继续进行，不增加首次 Apply，不用项目配置自行授予信任；其他符合规则的模块仍自动准备。信任记录由本机用户设置管理，不能验证受限运行方式的工具暂不启动相关实例。见[插件架构决策 Q79](research/2026-11-08-plugin-architecture.md)，许可和工具适配尚未实现。

### 跨平台包与独立 WASM

后续讨论采用的方案方向是 **一个安装包，多个独立 WASM 模块**，替代先前提出的 Windows DLL 方案。

```text
demo-plugin.zip
├─ plugin.toml
├─ modules/
│  ├─ ui.wasm
│  ├─ language_server.wasm
│  └─ formatter.wasm
├─ grammars/
│  └─ language.wasm
├─ queries/
│  ├─ highlights.scm
│  └─ injections.scm
├─ rules/
│  └─ defaults.js
└─ assets/
```

上面的目录和文件名是结构示意，包版本、协议、WIT、构建 target 和正式清单字段尚未冻结。简单插件可以只有一个模块；纯资源包无需附带空 WASM。

Rust 源码可以使用 workspace，将 UI、业务和轻量共享契约分开。UI 模块不得经共享依赖重新链接重型业务代码，其初始化也不得等待业务模块。插件作者使用 Rust 编译工具链，最终用户只安装已构建的包。

Q82 已确认 SDK 开发调试默认启动独立测试编辑器实例，使用独立配置、插件安装记录、可写数据、草稿和异常启动记录，直接加载本机编译输出，并提供编译后重新加载入口，无需反复打 ZIP 安装。普通用户仍使用官方目录或本地 ZIP，实验接口与权限要求继续适用，额外实例和编译工具链不进入普通启动路径。测试项目仍会被真实读写，开发者选择专门的测试项目；独立配置不等于系统沙箱。自动流程由后续 Q83 的逐插件开关控制。见[插件架构决策 Q82–Q83](research/2026-11-08-plugin-architecture.md)，尚未实现开发环境。

Q83 已确认“自动编译并重新加载”为每个插件单独可选的设置，入口为“设置 → 插件 → xxx 插件”。开启后，仅在主动启动的对应插件开发调试会话中，保存源码触发后台编译，完整成功后重新加载；关闭后使用手动构建和重新加载。编译失败保留运行版本，在途写操作仍等收尾，草稿与权限规则沿用既有约定。建议初始关闭，用户尚未单独指定默认值；不再把此前“默认自动”提案写为已采纳。当前仅有设计，未实现设置页面或自动编译流程。

Q84 已确认插件常规设置由宿主根据安装包中登记的名称、类型、默认值、说明与基础约束统一生成，提供键盘操作、搜索、恢复默认和基础校验；复杂设置允许插件通过 UI SDK 自定义，并通过宿主配置接口提交。静态声明随安装、更新准备，查看和调整普通设置不依赖插件业务进程启动或健康。自定义设置界面沿用既有模块条件与恢复约定；插件业务设置和宿主提供的开发开关分别管理。普通设置的作用域由 Q85 确认，提交生效由 Q86 确认，升级兼容与文件改写原则由 Q89 确认；现有启用规则继续遵守 `.nb/`、覆盖优先级与 Apply 约定。见[插件架构决策 Q84](research/2026-11-08-plugin-architecture.md)，尚未实现设置生成器或具体迁移协议。

Q85 已确认普通设置逐项声明可随项目保存或仅本机。可共享项采用项目显式值 → 全局用户值 → 插件默认值，项目值写入 `.nb/`，缺省表示继承；仅本机项写用户配置，声明允许时也可按项目分别保存本机覆盖。宿主显示当前值来源并校验允许范围，通用和自定义设置提交使用相同约定。Q83 开发自动编译开关仅本机保存，仍只作用于主动开启的开发会话，初始关闭仍为建议。项目内相对工具路径可按声明支持项目配置，不把所有路径统一限制为本机项；权限与信任记录沿用既有独立归属。见[插件架构决策 Q85](research/2026-11-08-plugin-architecture.md)，普通设置的提交生效按 Q86，尚未实现配置存储或范围校验。

对格式化等一次只选一个插件处理的功能，支持按功能和文件类型指定默认插件，当前项目覆盖全局选择，按 Apply 并完成必要保存后生效。项目配置仅记录插件身份，不指定版本。未指定默认值时，只有一个符合条件的插件便直接使用；多个候选时，在首次手动使用该功能时提供选择，启动不弹窗，正文保存不等待选择。默认选择只决定请求交给谁，不改变模块启用规则或其他插件的生命周期。

默认格式化插件不可用或格式化失败时，仅终止本次格式化并消息提醒，由用户自行处理错误；保留默认设置，不自动重试，也不提供临时换用其他插件处理本次的入口。用户需要改用其他插件时，通过原有设置与 Apply 流程处理。保存触发的格式化失败不阻断正文编辑与原保存流程，保存成功与否仍以实际写入结果为准；已终止请求的迟到结果不再应用。

单文档格式化由插件返回完整的一组修改，宿主核对文档身份、打开代次、内容版本和全部修改范围后整批应用，形成一次撤销记录。等待期间正文变化、请求取消或文档关闭/重开时，旧结果作废并消息提醒，不应用部分结果、不自动重算；用户自行再次触发格式化。成功后一次撤销可撤回整次格式化，其他用户编辑保持独立。跨文件文本修改方向已由 Q76 确认，具体协议及外部工具直接写盘的处理另行设计。

已开启保存时格式化的情况下，格式化阶段的总等待上限初始设为一秒，包含排队、准备、通信和结果校验。超时终止本次格式化并消息提醒，继续保存当前正文，拒绝迟到结果，不自动重试或换插件；明确失败或过期时提前结束等待。等待期间仍可编辑，写盘仅确认实际保存的内容版本。该预算只限制格式化附加的等待，不包含磁盘写入耗时。

手动执行单文档格式化的初始总等待上限为十秒，包含宿主接受任务后的排队、准备、通信和结果校验，等待期间显示 Formatting… 和可键盘操作的 Cancel。用户可以提前取消；超时或取消后使请求失效，拒绝迟到结果，按既定约定提醒，不自动重试或切换插件。该预算与保存时格式化的一秒上限分别计时，均待实测校准。

同一文档的相同手动格式化请求在任务未结束时共用当前任务，不重复执行或追加排队，也不重置十秒计时；成功后只应用一次结果。合并须核对文档版本、提供者、范围、选项及有效配置等确实一致。正文变化后仍按过期请求处理，不自动为最新正文重算；不同文档不会互相合并。

已开启保存时格式化且手动任务仍有效、与保存需要的格式化完全相同时，共用现有任务。截止时间取原手动任务十秒上限与进入保存格式化阶段后一秒中的较早者，重复触发不延长。及时完成则只应用一次结果后保存；超时或取消则终止这项共享格式化、提醒并继续保存当前正文，迟到结果不再修改正文。

用户于 2026-11-10 要求停止逐项追问格式化细节，参考 IDEA 与 VS Code 完成常规设计。提供整文档和选区格式化命令，选区能力由提供者声明；保存时格式化初版默认关闭，可按语言或文件类型设置，项目覆盖全局，沿用 Apply。普通格式化不隐含整理导入或代码修复，具体工具配置由提供者声明支持范围。错误消息不阻塞编辑，重复保存的同类故障合并提醒并保留日志。

未开启保存时格式化时直接保存，不额外等待已有手动任务；有效的手动结果稍后改变正文时显示未保存状态，不由格式化任务自动写盘。已开启但保存需要的格式化与手动任务不同时，保存流程优先，先使旧手动请求失效，再按一秒总预算处理，超时提醒并保存，拒绝旧结果。保存格式化进行期间的相同手动请求共用剩余预算；不同请求提示当前任务状态，不自动排队或延长等待。写盘只确认实际保存的版本，不能清除较新修改的未保存状态。这些并发细节是授权下的 Nanobug 设计选择，不是两款 IDE 完全相同的行为；依据和完整约定见[常规交互研究](research/2026-11-10-formatting-conventions.md)与[架构记录第 71 节](research/2026-11-08-plugin-architecture.md)。尚未实现或验证。

### 哪些内容需要可执行 WASM

| 内容 | 方案方向 |
| --- | --- |
| Rust 插件 UI 状态与交互 | 可独立编译为 UI WASM，打开视图时加载 |
| Rust 业务功能 | 按有独立生命周期的职责拆为 WASM |
| Tree-sitter grammar | 独立 grammar WASM，使用 Tree-sitter 对应 ABI 和加载器 |
| 高亮查询、注入查询、主题、图标、图片、代码片段 | 普通资源，不必为每项编译一个 WASM |
| JS 启用条件 | 由嵌入式 JS 引擎执行，无需编译成 WASM |
| 语法树、高亮范围、DrawList | 运行时数据，不是独立插件可执行文件 |
| GPUI 绘制、字体排版、原生输入、全局光标 | 宿主原生实现 |
| LSP 或其他原生工具 | Q69 已确认由宿主统一托管，允许指定已有工具路径，不强制转换为 WASM |

Tree-sitter grammar 与普通业务 WASM Component 不是同一种接口，不能仅按文件扩展名决定加载方式。Q65 已确认基础语法解析交给宿主管理的独立公共进程，与公共 JS 规则进程分开；高亮、折叠、基于语法的函数列表等功能可复用同一文档版本、grammar 及解析配置对应的基础结果。插件特有的类型检查、补全、编译器或 LSP 分析仍可自行实现，不强制统一到这份语法树。

公共解析服务在核心可编辑后准备，配置满足即安排适用资源，不增加首次使用门槛；项目关闭释放独占数据，共享数据按剩余所有者保留。用户接受公共进程故障可能暂时影响多个依赖功能，正文编辑和保存继续正常工作的取舍。具体文档同步、查询协议、资源预算和恢复策略尚待实现，实际性能收益需实测。见[插件架构决策 Q65](research/2026-11-08-plugin-architecture.md)。

### 可条件启用的模块

模块 ID 由插件声明，优先按职责命名，例如 `ui`、`language_server`、`grammar`、`preview`、`formatter`、`linter`、`indexer`、`search_provider`、`commands`、`project_discovery`、`file_provider`、`source_control`。

业务明确时也可叫 `export_pdf`、`link_checker`、`history`、`blame`。早期示例中的 `logic` 只是泛称，不是必须保留的模块类型。

补全、悬浮、跳转、重命名和诊断可能共用一个语言服务，不必机械地拆成多个 WASM。拆分依据是加载时机、依赖和执行生命周期。

## JS 模块启用规则

### 配置体验

用户在设置管理中选择插件并编辑其 JS 规则；每个插件有独立配置，插件提供默认规则。用户已表示模块 ID 的补全提示由插件提供，本轮不继续展开该话题。

规则提供 `Current project` 与 `All projects` 两个作用范围，默认选择当前项目。按模块使用当前项目覆盖、全局用户覆盖、插件默认规则的继承顺序；规则页的修改先保留为草稿。按 Apply 后，通过语法及冲突检查并完成必要的规则保存、已应用版本记录，再切换为有效配置；保存失败时保留草稿，继续使用此前有效规则并显示应用失败。保存与检查在后台进行，正文不等待。

第一次打开带 `.nb/` 的项目时自动载入已有规则，无需先按 Apply；仍先保证正文可编辑，再后台检查、判断并准备符合条件的已安装插件模块。项目中明确配置的模块规则覆盖全局规则，true 和 false 都有效；未配置的模块继续逐层继承。此覆盖仅作用于当前项目。

项目已打开时，外部编辑器或 Git 改变 `.nb/` 中的启用规则后，也先提示待应用，按 Apply 并通过语法检查后再切换；规则读取的 `package.json` 等数据变化仍自动重新判断，不要求手动 Apply。草稿与外部修改冲突时保留双方内容，提供差异查看，用户选择版本或手动合并后再按 Apply 生效，期间继续使用此前有效的规则内容。

对于已有应用记录的项目，关闭或重启后恢复上次已应用的规则内容，保留待应用修改、草稿及冲突内容；规则恢复后按当前有效数据重新判断，不把未应用修改因重启自动生效。恢复所需版本保存在本机，`.nb/` 仍为项目配置来源；具体持久化协议继续设计。

项目配置引用但本机尚未安装的插件，在插件管理器中显示 `Not installed` 并提供 Install 入口，由用户选择安装，正文不等待下载或安装。安装完成后按已生效且受影响的规则重新判断，条件满足才准备模块；安装操作不自动应用规则草稿或待应用外部修改。

用户已明确否决项目指定插件版本：项目配置只能声明使用哪个插件及其模块规则，不能指定插件包的准确版本或版本范围。插件包仍按自身版本发布。用户随后单独确认：点击 Install 时，由宿主选择可获取且兼容当前编辑器、平台及必需能力的最新稳定版；如果不存在可安装的兼容版本则显示原因，因编辑器过旧导致不兼容时提示升级。该决定确定首次安装的默认选版，当前来源范围按 Q80 为官方插件与本地 ZIP。

用户已确认：项目级配置存放在 `<项目根目录>/.nb/`，该目录作为编辑器可读的项目配置入口，当前项目的插件规则也保存在其中。目录内部文件组织与格式继续设计。全局规则仍采用 `用户配置根/plugins/<插件ID>.js` 的概念目录；实际用户配置根位置待定，不从这条相对路径推导旧项目的数据目录规则。详见[插件架构决策 Q37–Q44](research/2026-11-08-plugin-architecture.md)。这些是设计决定，尚未实现项目配置读写。

JS 只做条件判断与模块选择，Rust 宿主负责权限检查、生命周期和实际加载。复用 JS 引擎及已加载函数；按文件、项目依赖、设置变化等事件重新评估，不让 JS 参与每帧字符绘制或光标动画。

### 拟定接口示例

以下配置语法是讨论方案，不是已实现接口。

```js
// javascript.js：正文或嵌入代码块需要 JavaScript 时启用对应 grammar。
export default {
  modules: {
    grammar: ctx => ctx.languages.includes("javascript"),
    language_server: ctx => ctx.file.extension === ".js",
  },
};
```

```js
// vue3.js：示例采用已解析的 Vue 主版本，未知版本不匹配。
function matchesVue3Project(ctx) {
  return (
    ctx.project.rootFiles.includes("package.json") &&
    ctx.project.dependencies.vue?.major === 3
  );
}

export default {
  modules: {
    grammar: ctx => ctx.languages.includes("vue") && matchesVue3Project(ctx),
    language_server: ctx => ctx.file.extension === ".vue" && matchesVue3Project(ctx),
  },
};
```

候选上下文包含文件扩展名、当前及嵌入语言、项目根文件列表、解析后的依赖版本。宿主缓存这些信息，批量传给脚本；不要求脚本每次自行读文件和解析依赖。

规则语义方向：`true` 允许当前上下文启用，`false` 不为当前上下文启用。按后续 Q38/Q42 确认的覆盖顺序，当前层缺省或 `undefined` 时继承下一层：项目规则继承全局规则，全局规则继承插件默认规则；明确的 true/false 覆盖低优先级规则。宿主汇总所有文档的需求；一个文档返回 `false`，不能停掉另一个文档仍在使用的模块。

用户只覆盖部分模块时，其余保留默认配置；修改成功后重新评估，出错则显示错误并保留上一份有效配置，插件更新保留用户配置。具体优先级、资源释放策略、脚本执行预算和诊断格式待定。

### 语言选择和嵌入高亮

用户举出的场景必须覆盖：

1. `.js` 调用 JavaScript 对应模块，`.md` 调用 Markdown 对应模块。
2. 项目根包含 `package.json`，依据 Vue 版本选择 Vue 插件。
3. Markdown 代码块识别出其他语言后，只加载必要的语言解析与高亮资源。

Vue 条件存在需要确认的语义差异：用户原话是“版本大于 3 用 Vue3，否则 Vue2”，后续示例采用“主版本等于 3 / 等于 2，未知不匹配”。正式规则必须明确是 `>=3`、`>3` 还是 `major === 3`，以及未知版本、版本范围和多个依赖位置如何处理；不能把未知版本自动归为 Vue2。

Markdown 的方案流程为：Markdown grammar 识别代码块 → 得到语言标识 → 更新语言上下文 → 评估对应插件规则 → 加载该语言 grammar 与查询 → 对块内容高亮。此过程不应默认启动该语言插件全部业务模块或 LSP。

基础语法高亮与 LSP 语义高亮可以叠加；grammar、查询、语法树、高亮范围和最终 GPU 绘制需要分清职责。语言注入不等于完整的嵌入语言补全、跳转和格式化，后者另需设计。

## 内部窗口与插件布局

### LazyVim 参考结论

本次调查区分了 Neovim 核心窗口、插件内部布局和 Edgy 等可选布局管理器：普通分栏可嵌套组合，浮窗覆盖在分栏之上；插件可以计算一组内部窗口的几何位置。可选 Edgy 可把面板按上下左右分组，但不会自动给所有插件提供“底部永远只显示一个”的通用互斥策略。

V2 可借鉴窗口与内容分离、嵌套分栏、浮层坐标和统一焦点管理，而不照搬所有 LazyVim 插件布局。已制作的 34 种布局图例是参考图鉴，不是 34 项全部必须实现的功能清单。

### 宿主和插件的布局边界

方案方向：宿主管理顶层分栏树、区域分配、焦点、尺寸、层级和窗口移动；插件管理分配区域内部的布局与交互。插件通过通用接口申请侧边区域、底部区域或浮层，不能绕过宿主各自抢占全局空间。

需要设计的操作包括：方向切换焦点、调整尺寸、交换窗口、移动到某方向、显示隐藏、关闭和恢复。Neovim 的 `Ctrl+w` 加大写 `H/J/K/L` 可作为“移动窗口”参考，`Ctrl+h/j/k/l` 可作为“切换焦点”参考；V2 的实际键位没有定案。

### 多面板策略

底部已采用单窗口覆盖切换作为当前默认，其余策略留待布局专题：

| 策略 | 表现 | 状态 |
| --- | --- | --- |
| 单活动面板 | 新面板在同一个底部窗口中覆盖切换原显示内容 | Q74 已确认当前默认 |
| 标签或选择器 | 多面板注册到同一区域，用户切换当前项 | 未确认，布局讨论暂缓 |
| 多面板并排或堆叠 | 同一区域同时显示多个内容 | 未确认，布局讨论暂缓 |

底部以外的默认策略、具体切换入口、面板最小尺寸、空间不足、布局持久化、插件自己的多窗口组如何移动，继续待定。隐藏面板不等于关闭文档、销毁插件或终止后台任务，继续遵守已确认的模块生命周期和输入保留规则。

[Q74](research/2026-11-08-plugin-architecture.md) 已按用户修正收敛为“先默认只占一个底部窗口，覆盖切换”，不将上一轮的标签和手动分栏建议视为已获采纳。当前停止追问布局，继续插件架构讨论；尚未修改布局实现或 UI 预览。
